## 0. 修订记录（2026-09-30，老师评审意见）

> 本节为最新决策，与前文冲突处以本节为准。`docs/superpowers/plans/2026-09-28-xianying-mvp.md` 中受影响的 Task（悬浮窗三件套、预警/倒计时）需按本节调整后再执行。

### 0.1 背景

老师评审结论：完整规格的方案落地有难度；结合"不懂代码 + AI 写码"的实际情况，应先零代码验证，再降级到「仅抖音 + 仅时长 + 前台计时 + 到点返回桌面」的自用 MVP。

### 0.2 硬约束：不懂代码 + AI

代码由 AI 编写，用户无法自行调试 → 技术选型原则：

- **只走确定性路径**：二元判断（前台包名 == 抖音）可行；模糊判断（是否在播视频、页面内容识别）不可行
- **真机调试次数必须压到接近零**：所有"需要真机反复看日志、调参、改判断逻辑"的方案一律不做
- **自用**：单机、单人、手动授权、无需分发与体验打磨，错误处理从简

### 0.3 新增前置步骤：零代码验证（先于任何开发）

用成熟自动化工具（MacroDroid / Tasker 类）配置规则「打开抖音开始计时，N 分钟后按 Home」，验证两个最危险的假设：

1. 这台手机能否检测到"抖音在前台"（Accessibility 事件是否可用、是否被厂商 ROM 限制）
2. 能否到点自动返回桌面（`GLOBAL_ACTION_HOME` 类操作是否生效）

三种结局都有价值：

| 结论 | 行动 |
|------|------|
| ✅ 全部跑通 | 技术风险解除；若工具本身够用，可不开发 App |
| ⚠️ 能检测、不能回桌面 | 方案降级为"到点强提醒"，放弃自动返回桌面 |
| ❌ 都不行 | 此路不通，换技术路线（帧差/录屏）或放弃 |

**用别人的成熟工具试错，比用自己的代码试错便宜得多。**

### 0.4 MVP 功能边界再降级

MVP = **仅抖音 + 仅时长 + 前台计时 + 到点返回桌面**，即：

> 打开抖音 → 抖音前台期间累计计时 → 累计到 N 分钟 → 执行返回桌面

相对本设计文档第 3 节原 MVP 范围，以下功能**移出 MVP**（降级为后续可选增强，按序）：

| 功能 | 处置 |
|------|------|
| 悬浮窗设置面板（每次弹窗选时长） | 改为在限映 App 内预设固定时长，不弹窗 |
| 剩 1 分钟预警条 | 后续增强 |
| 全屏警告 + 10 秒倒计时 + 震动 + 提示音 | 后续增强；MVP 直接触发返回桌面 |
| 30 分钟脱离会话自动解除 | 后续增强；MVP 允许额度跨进出保留（离开暂停/重进继续仍保留，这是"前台计时"的自然语义） |

明确不做（维持原判断）：条数/双重限制模式、5 秒有效计数、视频切换识别、快手/B站、直播/图文区分。

### 0.5 到点行为决策（2026-09-30 与用户确认）

评估过三个方案：A 直接送回桌面 / B 警告+倒计时再送回 / C 暂停视频禁止播放。

- **MVP 采用 A：到点直接执行返回桌面**——技术确定性最高（GLOBAL_ACTION_HOME），符合柔性戒断理念（红线：退出后无冷却、可立即重开，靠摩擦不靠强制）
- B（预警条 → 倒计时 → 返回）保留为后续增强，方向正确但增加一整套悬浮窗/震动/提示音的开发与调试量
- **C 明确否决**：普通 App 无法控制抖音播放器，只能靠模拟点击或挡触摸悬浮窗间接实现，全是模糊路径，违反 0.2 硬约束；且"禁止播放"与"自主管控、无冷却"的产品红线冲突，堵不住重开只会变成攻防

### 0.6 视频切换识别策略——竖屏/非竖屏分流（2026-09-30 晚定稿，P2 排期）

用户设计的总框架：**竖屏信息流走画面帧差判定；非竖屏模式走视频标题、发布者、播放进度、画面主体多维度综合判定**。结合实测落地为三层，严格遵守 0.2"确定性优先"原则：

| 层 | 手段 | 状态 |
|----|------|------|
| 竖屏·抖音 | MediaProjection 低清帧差（抖音不发滚动事件，唯一需要④画面识别；戒断退出自动停录屏） | ✅ 模拟器闭环 |
| 竖屏·B站/快手 | 无障碍 TYPE_VIEW_SCROLLED 直连，无需录屏 | B站✅模拟器实测；快手待真机 |
| 非竖屏·第一层 | ~~"新视频详情页出现"按 Activity 窗口事件计数~~ **已实测否决（2026-09-30 晚，模拟器 B站 9.x）**：打开视频/页内换相关视频发 UnitedBizDetailsActivity 事件对（2 条~2 秒间隔），但**评论面板关闭、子页面返回也发同类事件**（1~2 条）——className 无法确定性区分"真的换视频"与"关面板返回"，违反 0.2 确定性原则，不做 | ❌ 已否决 |
| 非竖屏·第二层 | 读标题/发布者/进度判定：需开 canRetrieveWindowContent（现为 false）+ 每平台控件规则，App 改版即失效。当前产品定位下的替代方案：**横屏长视频归"仅时长"模式管**（前台计时已覆盖，零新代码） | P2，确有需求再做 |
| 非竖屏·第三层 | 画面主体识别（视觉模型/OCR） | P3，规则穷尽后再议 |

已知边界（如实告知用户）：非竖屏第一层只计"打开过的视频页"，同一页面里连续点相关视频少计；竖屏直播/图文误计风险靠阈值与 gating 压制，真机重校（TESTING.md D5/D6/E4）。

## 1. 项目背景与目标

限映是 Android 本地短视频使用自主管控工具：使用者自己决定本次短视频使用额度，通过单次 Session 柔性管控，无云端、无历史记录、无家长监控。完整产品需求见根目录 `CLAUDE .md`。

本次交付 **MVP**：跑通"仅时长模式"完整闭环——

> 打开限映 → 开总开关 → 打开抖音 → 弹设置面板 → 选"仅时长 N 分钟" → 抖音前台期间计时（离开暂停、重进继续）→ 剩 1 分钟顶部预警 → 时间到全屏警告 + 震动/提示音 + 10 秒倒计时 → 返回桌面 → 脱离满 30 分钟会话自动解除。

## 2. 已澄清的需求决策

| 决策点 | 结论 |
|--------|------|
| 识别路线 | Accessibility 优先；帧差/MediaProjection 仅作后续备选 |
| 测试设备 | 有真机但不便连线 → 验证与调试不依赖 adb/logcat，APK 传手机自测 |
| 设置面板粒度 | 每次新会话才弹；短暂切出（<30 分钟）再进入不弹、沿用剩余额度 |
| 时长口径 | 目标语义为"只在播放时计时"；**MVP 降级为"抖音在前台即计时"**（播放判定属后续增强） |
| 直播/图文/评论区 | 不计额度、会话保持、脱离计时清零（仅离开抖音才累计脱离） |
| 多 App 会话 | 各自独立会话（MVP 仅抖音，架构预留 targetApp） |
| 强制退出 | 以 Accessibility `GLOBAL_ACTION_HOME` 返回桌面为基准，不假设能杀死第三方 App |
| 实施路线 | 用户选择直接开发 MVP（跳过独立 Phase 0 工程）；开发顺序风险前置：先监控核心后 UI 壳 |
| 网页交互 Demo | 仅规划，不在本期范围 |

## 3. MVP 范围

> ⚠️ 2026-09-30 修订：本节为原始范围，**已被第 0 节 0.4 的降级边界取代**，仅作历史保留。

**包含**：全局开关、Session 状态机、仅时长/无限次两种模式、顶部预警、全屏警告（震动+提示音+10 秒倒计时）、返回桌面、30 分钟自动解除、基础厂商保活处理。

**不包含**（后续迭代）：仅条数/双重限制模式、5 秒有效计数、视频切换识别、快手/B站 Detector、直播/图文内容区分、设置面板记忆。

## 4. 总体架构

```
com.xianying.app
├── MainActivity / ui          # 极简主界面：总开关 + 权限引导
├── service/
│   ├── MonitorAccessibilityService  # 唯一事件入口：窗口变化事件
│   └── KeepAliveForegroundService   # 前台服务：保活 + Session 宿主
├── session/                   # SessionManager 状态机（纯 Kotlin，可单测）
├── control/
│   ├── OverlayController      # 面板/预警条/全屏警告 的窗口管理
│   └── ExitExecutor           # 倒计时结束执行 GLOBAL_ACTION_HOME
└── model/                     # SessionConfig / SessionStatus / TargetApp
```

关键决策：

- **前台识别不依赖 UsageStats**：用 AccessibilityService 的 `TYPE_WINDOW_STATE_CHANGED` 事件直接获取前台包名，比 UsageStatsManager 轮询实时且少一个特殊权限；UsageStats 留作兜底。
- **悬浮窗权限一举三得**：设置面板、预警条、全屏警告统一走 SYSTEM_ALERT_WINDOW（Android 10+ 后台启动全屏界面受系统限制，SAW 是最可控路径）。
- **平台适配解耦**：SessionManager 不含任何抖音特定逻辑，包名识别收敛在配置层，为后续 DouyinDetector/KuaishouDetector 预留。

## 5. Session 状态机

```
IDLE（无会话）
  │ 打开抖音（全局开关 ON）
  ▼
SETTING（弹出设置面板）
  │ 选"仅时长 N 分钟"            │ 关闭面板/选无限次
  ▼                              ▼
TIMING（计时中）                PASS_THROUGH（放行，仅记录在抖音内）
  │ 切出抖音/锁屏                │ 切出抖音/锁屏（同样累计脱离时长）
  ▼                              ▼
PAUSED（暂停，累计脱离时长）◄─────┘
  │ 注：WARNING 是 TIMING 的警示相位（计时继续），
  │     PAUSED↔TIMING 的迁移规则对 WARNING 相位同样适用
  │
  │ 重进抖音（脱离<30min）──→ TIMING（继续剩余额度）
  │ 重进抖音（脱离<30min）──→ TIMING（继续剩余额度）
  │ 脱离 ≥30min ──→ IDLE（会话销毁，下次进入重新弹面板）
  │ 剩余 ≤1分钟
  ▼
WARNING（顶部轻量预警条，计时继续）
  │ 额度用完
  ▼
FINAL_COUNTDOWN（全屏警告+震动+提示音+10秒倒计时）
  │ 倒计时结束（或用户中途自己退出抖音）
  ▼
EXITING（GLOBAL_ACTION_HOME）→ ENDED → IDLE（无冷却，可立即重开）
```

## 6. 数据流

```
抖音窗口变化事件（AccessibilityService）
        │ 包名 == com.ss.android.ugc.aweme
        ▼
SessionManager.onForegroundChanged(inShortVideo: Boolean)
        │ 状态机迁移，对外仅暴露状态 + 剩余额度
        ├──→ OverlayController（面板/预警条/全屏警告）
        ├──→ KeepAliveForegroundService（常驻通知显示"剩余 X 分钟"）
        └──→ ExitExecutor（FINAL_COUNTDOWN 结束返回桌面）
```

- SessionManager 为纯 Kotlin 状态机，不依赖 Android UI；时间源（`elapsedRealtime`）通过接口注入，便于单测模拟快进。
- 脱离计时定义：不在抖音前台（其它 App/桌面/锁屏）→ 累计 awayDuration；在抖音内任何页面 → 脱离清零、会话保持。
- 震动用 `VibrationEffect`，提示音用 `ToneGenerator`。

## 7. 权限模型

| 权限 | 用途 | 降级方案 |
|------|------|---------|
| AccessibilityService | 前台识别 + 返回桌面 | 无（失效则 fail-open 放行 + 通知提醒修复） |
| SYSTEM_ALERT_WINDOW | 面板/预警条/全屏警告 | heads-up 通知 + full-screen-intent 通知 |
| 前台服务 + 电池优化白名单 | 保活 | 常驻通知引导设置 |

主界面提供逐项权限引导。

## 8. 错误处理与边界

原则：**fail-open** —— 工具故障绝不妨碍用户正常用机，失效即静默放行 + 常驻通知提醒。

| 场景 | 处理 |
|------|------|
| Accessibility 被杀/被关 | 前台服务检测断连 → 通知变"监控已失效，点此修复" |
| 悬浮窗权限被关 | 见上表降级 |
| 手机重启 | 开关状态本地记忆；AccessibilityService 系统自动恢复；Session 清空；前台服务需打开 App 一次重新激活 |
| 倒计时期间用户自行退出抖音 | 视为已离开，直接 ENDED，不执行返回桌面 |
| 用户改系统时间 | 全部计时用 `elapsedRealtime`（单调时钟），不受影响 |
| 面板交互 | 点面板外/返回键 = 无限次放行（强制选择但不强制设限） |
| 快速反复进出抖音 | 状态机迁移幂等，无副作用 |
| 分屏/抖音多进程 | MVP 不处理分屏；以主进程窗口事件为准 |

## 9. 测试策略（2026-09-30 修订：模拟器先行，真机终验）

1. **单元测试**（本机，无需任何设备）：SessionManager 状态机全路径，注入假时钟覆盖每条迁移边。
2. **模拟器自测**（AVD，Android Studio 自带，非虚拟机）：开发期主力。
   - 验：APK 安装启动、主界面 UI、状态机全流程、无障碍事件流转、前台检测 + 回桌面机制
   - 方法：用**替身 App**（模拟器自带 Chrome/设置）当目标 App 测——检测逻辑是"包名 == 目标"，与具体 App 无关
   - **模拟器上不装抖音**（抖音有模拟器检测，行为不可信）
3. **真机终验**：模拟器跑通的版本出 APK 传手机，只验模拟器验不了的：抖音本体、厂商 ROM 保活/电池白名单、真实使用场景。维护 `TESTING.md` 手测清单。
4. **构建交付**：本机 `gradlew assembleDebug` 出 APK → 微信/QQ 传手机安装。

## 11. 风险与应对

| 风险 | 应对 |
|------|------|
| 抖音 Accessibility 能拿到的信息不足 | 已选风险前置的开发顺序：监控核心最先真机验证；不足则调整识别策略（帧差备选） |
| 国产 ROM 杀后台 | 前台服务 + 电池优化白名单引导；针对实测机型补充设置指引 |
| SAW 在部分 ROM（MIUI 等）需"后台弹出界面"权限 | 权限引导页覆盖，真机实测补充 |
